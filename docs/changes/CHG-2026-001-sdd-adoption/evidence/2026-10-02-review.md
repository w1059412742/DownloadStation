## 2. 主要发现与处理方向

以下优先级表示补齐接入工作的先后。对于代码问题，本轮结论以静态调用链为限；未声称已在 HTTP、浏览器或生产环境复现。

### R01（高）：公开版本与下载入口缺少父软件发布状态检查

[DownloadController.cs 第 19–43 行](../../../../03_src/DownloadStation.Server/Controllers/Public/DownloadController.cs#L19) 的下载链检查版本存在、软件 ID 匹配、版本可见以及文件存在；公开版本列表调用 GetBySoftwareIdAsync。[VersionService.cs 第 27–49 行](../../../../03_src/DownloadStation.Server/Services/Implementations/VersionService.cs#L27) 只按软件 ID 和版本 IsVisible 过滤，GetByIdAsync 也未关联父软件状态。公开软件列表/详情另有 Published 限制。

因此，当父软件为 Draft 而关联版本仍可见时，直接请求版本列表/下载的调用链缺少同等发布限制。版本映射还包含 FilePath，公开列表会返回该字段。现有 CAT 的 REQ-CAT-001-007 已提出公开边界，但接入调查没有准确登记实际差距；契约参考只把路径暴露描述为后台风险，也不准确。

处理：补齐当前事实与候选目标的差异记录；确认公开发布边界后，为代码修复建立单独 Change 和回归证据。不要把列表页隐藏当成下载权限检查完成。

### R02（高）：旧需求和代码新增行为没有逐项承接

旧 PRD 中的多截图相册、历史版本折叠、完整校验码查看/复制、更新日志渲染、存储空间和下载 Top 10 等，没有形成足够明确的规则、验收或“历史要求已移出范围”的决定。代码中已有分享链接、免责声明、后台预览、上传进度/拖拽等能力，也没有完整纳入规格。

单平台/多平台、Cookie/JWT、Markdown/HTML 是不同来源之间的目标冲突，不能以“当前代码能运行”自动裁决。尤其会话冲突尚未进入原冲突表。

处理：对第 4 节的每项给出确定去向：候选目标、历史参考、明确移出范围、或有证据的已确认目标。补齐原文和当前代码的事实是 agent 的工作；只将影响产品结果而依据不足的决定交给负责人。

### R03（高）：接口或模型存在被误当成用户流程完整

[扫描页 Files.vue 第 96–98 行](../../../../03_src/DownloadStation.Web/src/views/admin/Files.vue#L96) 的“关联到软件”按钮只弹出“功能尚在开发中”。[管理详情页 SoftwareDetail.vue 第 609–620 行](../../../../03_src/DownloadStation.Web/src/views/admin/SoftwareDetail.vue#L609) 则存在另一条手动输入路径绑定的调用。原能力地图笼统记录“文件扫描/绑定”会掩盖扫描结果一键绑定未实现的事实。

截图也有实体、数据库配置和查询 DTO，但调查范围内未找到独立截图关联写入、管理相册以及公开相册/灯箱的完整链路。正文编辑器内的图片不是独立截图相册。

处理：拆清“扫描”和两条“绑定入口”，按 UI → API → 服务 → 数据/文件 → 公开消费者逐段标明已实现、占位、局部实现及未验证状态。

### R04（高）：规格可验证性不足，尚不能作为 agent 的明确实施输入

4 条需求未被 AC 显式引用：REQ-ADM-001-007、REQ-CAT-001-004、REQ-DST-001-008、REQ-OPS-001-004。这不表示它们必须恰好有一条独立测试，但必须有明确验收或适当检查覆盖。

[管理规格 AC-ADM-001-002](../../../../docs/specs/admin/F-ADM-001-admin-management.md#L57) 将分类、平台、标签、软件的创建/编辑/关联/删除压成一个场景，Then 只写“符合确认规则”，没有规则的具体内容或精确引用。看板也只有“按确认口径”，无法判定是否通过。功能组合过粗和未决口径不能靠加上 EARS/Given/When/Then 字样解决。

[Docker 规格 REQ-OPS-001-001](../../../../docs/specs/operations/F-OPS-001-docker-deployment.md#L13) 要求前后端合进同一个镜像，但第 63 行又保留单容器/分离部署选择。用户确认的是 Docker 发布，不能把具体拓扑当成已确认的同义条件。

处理：在原四份 Spec 内拆分可独立验证的规则，写明适用的权限、状态、失败、边界和副作用；AC 使用可观察结果或精确规则引用。未决定的目标保持 draft，不把未知值填成默认业务规则。

### R05（中）：项目入口没有完整落实技能协作和阶段流程

[AGENTS.md 场景路由和验证纪律](../../../../AGENTS.md#L12) 未明确绑定 sdd-specification-workflow、sdd-implementation-workflow、sdd-bugfix-workflow、sdd-reverse-engineering-workflow；全文没有 sdd-documentation。第 35 行“实施使用 TDD 规则时”是条件式，不能保证适用的自动化行为检查先失败、再实现、再回归。

项目旧 [设计技能第 8 行](../../../../.agents/skills/design/SKILL.md#L8) 仍自称“所有编码工作的唯一技术准绳”。根 AGENTS 已说旧技能只作工作资料，但旧文件正文和新基线的权威关系仍容易混淆。

处理：在现有 AGENTS 明确四个场景入口、共享文档规则的必读/必执行要求、相应收尾一致性审查模式，以及 TDD 适用和例外证据。技能不会因为写了名字就由系统自动形成可靠调用链；主 agent 应按场景技能说明实际读取并执行共享技能。旧技能作为历史参考或改为当前权威文档入口。不要再建立平行规则源。

项目初期/新阶段应先整理范围和依赖，讨论确认具体目标后分配实施任务；中期变更保留目标差异和 Change；Bug 修复先对照已有正确目标定位根因，只有目标本身需要纠正时才改 Spec；存量接入先完成证据调查和逐项确认，再进入正常工作流。原文只有一般原则，还没有完整落实这些执行条件。

### R06（高）：Docker 已收集输入，但存在确定的静态阻碍

1. [publish.ps1 第 16 行](../../../../03_src/publish.ps1#L16) 的镜像标签字符串中，变量后紧跟冒号。本轮只读 PowerShell Parser 实际返回 1 个 InvalidVariableReferenceWithDrive 错误，脚本不能正常解析；没有执行该脚本或镜像推送。
2. 前端 [http.ts 第 4 行](../../../../03_src/DownloadStation.Web/src/api/http.ts#L4) 使用同域请求，[Dockerfile.Web 第 19–31 行](../../../../03_src/Dockerfile.Web#L19) 的 Nginx 配置只有静态 fallback，没有 /api 或 /uploads 代理；[分离 compose](../../../../03_src/docker-compose.yml) 将前后端暴露在不同端口。现有仓库输入没有把这条浏览器请求链接到后端。外部已有反代可补这条链，但当前文档和配置未给出证据，不能仅列为可正常运行的候选路径。
3. 单容器和分离部署的上传/日志持久化配置不同，不能泛化成同一事实。数据库 FilePath 的 Windows→Linux/NAS 路径转换、运行权限与旧数据兼容也没有完整整理。
4. [Program.cs 第 125–134 行](../../../../03_src/DownloadStation.Server/Program.cs#L125) 在迁移异常时记日志后继续，发布失败处理、备份一致性和恢复匹配仍只有轮廓。未发现 .dockerignore；Docker 构建上下文、依赖安装和重复构建尚未验证。
5. [publish.sh](../../../../03_src/publish.sh) 包含自动 reset/pull 及 ch *；本轮未运行它。本轮发现的 PS 语法错误与历史记录中的 bash 可疑命令都应有准确处置。

处理：先确认最小正式发布路径并修正文档内的拓扑冲突，再将脚本、代理、持久化及恢复问题划入对应的配置/修复 Change。在具备 Docker 的环境获取实际镜像构建、启动、API/上传/下载、临时卷重建和恢复证据，最后才能声称发布路径已验证。

### R07（中）：失败、恢复和关联边界没有足够反向调查记录

已定位的其他事实包括：绑定不存在文件仍可保存大小为 0 的 Pending 记录；物理删除异常被吞掉而数据库记录仍删除；管理 UI 删除版本始终传 physicalDelete=true，不能等同 API 提供的两种选项都可操作；哈希后台只查询 Pending，崩溃后 Computing 没有自动恢复路径；同平台重名只是前端预检查，没有服务端写入/数据库组合唯一约束；分类只拒绝直接自父，没有间接环校验。

这些事实不等于本轮已经批准全部修复目标，但必须进入现状与差距记录，不能一概用“CRUD/哈希/删除接口已存在”代替边界调查。登录错误的 HTTP 状态与 body code、下载的文本错误和认证中间件响应也不完全同构；[HTTP 契约参考第 13 行](../../../../docs/contracts/http-api.md#L13) 的“失败响应使用相同外壳”过度概括。WeatherForecast 无产品消费者但仍有可达 API，不能记成不可达死代码。

### R08（中）：原调查的完成表述与证据粒度不足

原 Change 第 18 行“初始和交付前工作区无输出”不准确，文档交付本身已有工作区改动。原计划/进度称“完整调查”，但本轮发现上述遗漏。原证据表以通配符和模块为主，不能逐行为追溯。2026-10-02 的构建与数据库检查只有现有记录，本轮未重做；不能将其标为 2026-10-02 新测试。

SQLite“可能包含历史编码问题”尚无本轮独立证据，不能只依据终端显示异常认定数据库内容损坏。本轮未打开数据库，也未运行迁移。

处理：明确追加复核更正，保存本轮输入哈希与实际输出，把调查完成、目标 approved、实现 verified、已发布分开。本报告是既有 Change 的证据附件，不是第二套 Spec。

不需要为了上述缺口再加一套“需求/设计/计划/测试”永久目录。应把现有四份 Spec、project、契约、接入 Change 和 AGENTS 写实、关联准确。

## 6. 补齐顺序与完成条件

1. **先补证据和覆盖。** 按第 4 节完成旧条款、新增行为和跨端调用链的事实调查，把未实现/占位/部分实现与未验证分开，纠正原能力地图和契约事实。这一阶段由 agent 完成，不能把可查事实交给负责人猜。
2. **再补可判定的 draft Spec。** 原四份 Spec 内补规则、边界、失败/恢复和 AC；合并重复定义，链接契约/长期机制。初始接入资料不是让 agent 同步执行代码功能改造的授权。
3. **落实 agent 执行入口。** 修订现有 AGENTS 的四场景和两个共享技能路由、TDD、完成核对及状态要求；整理旧技能为历史参考/导航，不另建平行规格。
4. **集中确认产品与正式运行边界。** 让负责人审阅具体文件差异，决定平台关系、正文/日志格式、Cookie/JWT 会话、默认版本/计数、旧 UI 条款和正式 Docker 路径。确认可以按独立能力或阶段逐项进行，不以一条“同意”批准全部未知内容。确认范围的 Spec 才能 approved。
5. **随后分配实施。** 对已批准目标与当前代码的差距建立相应 feature/fix/config Change，关联 REQ/AC 和前后端任务。进行适用的 TDD、关键路径验证和一致性审查；不要把本次接入 Change 变成所有历史缺陷的大修记录。
6. **最后验证 Docker 交付。** 在可用环境完成镜像构建、启动、API/资源/下载链、持久卷重建及恢复；保存证据和适用配置，分别说明实现 verified、是否合并、是否实际发布。

可以宣称“需求整理完成”的条件：调查范围内每个来源项有明确去向；目标冲突有实际决定或明确未决边界；正式实施范围的 REQ/AC 可判定且可追溯，具体文件差异获确认。可以宣称“完整接入 SDD”的条件还包括：项目入口和技能执行链已落实，当前实现差距有准确记录及归属，审查/状态机制有效。两者都不等于历史代码已全部修好或 Docker 已发布。
